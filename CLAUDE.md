# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Somnium is a 2D top-down Unity game (URP, Unity 6 / `6000.0.65f1`). It uses the new Input System, NavMesh (via the community `NavMeshComponents` package vendored under `Assets/Assets/NavMeshComponents`) for future enemy AI, and Unity's Visual Scripting package is a dependency.

## Working with this repo

This is a Unity project, not a CLI/npm/CMake project — there is no command-line build/test/lint step. Development happens through the Unity Editor:

- Open the project in Unity Editor **6000.0.65f1** (see `ProjectSettings/ProjectVersion.txt`) — using a different version will cause Unity to reimport/upgrade the project.
- `Somnium.sln` / `Somnium.slnx` are generated by Unity from the C# assemblies; regenerate via Editor > menu (Assets > Open C# Project) rather than hand-editing.
- There is no `Assets/Assets/Scripts/**/Tests` or `com.unity.test-framework` usage yet, so there are no tests to run.
- To verify a change compiles, the practical option is opening the project in the Unity Editor and checking the Console for compile errors (there is no headless build script in this repo).

## Directory layout

Unity conventionally nests project content under `Assets/`, but this repo has an extra `Assets/Assets/` level — most game content (scripts, sprites, prefabs, animations, UI) lives under `Assets/Assets/`, while `Assets/Scenes/` and `Assets/Settings/` sit directly under the top-level `Assets/`. Keep this in mind when locating or creating files:

- `Assets/Assets/Scripts/` — gameplay code, organized by feature (see Architecture below)
- `Assets/Assets/Prefabs/` — `Guns/`, `Items/`, `Sounds/`
- `Assets/Assets/Animations/` — per-character/gun animator controllers and clips
- `Assets/Assets/Sprites/` — organized by category (`Player_Sprites`, `Enemy_Sprites`, `Gun_Sprites`, `Item_Sprites`, `Map_Sprites`, `Particle_Sprites`, `Ui_Sprites`)
- `Assets/Assets/NavMeshComponents/` — vendored third-party package (2D NavMesh baking components), not project-authored code
- `Assets/Scenes/` — `OutsideHouse.unity`, `TestHub.unity`, `UI.unity`
- `Assets/Assets/Scripts/Player/PlayerInput/Somnium.inputactions` — the Input System action map used by player scripts (`OnMove`-style handlers via `InputValue`)

`Assets/Assets/Scripts/Enemy/`, `Scripts/Interactable/`, and `Scripts/Items/` exist as folders but are currently empty — enemy AI and interaction/item systems are planned but not yet implemented in code.

## Architecture

### Player state machine

Player movement/behavior is a hand-rolled state machine, not Animator-driven:

- `PlayerStateController` (`Assets/Assets/Scripts/Player/PlayerStateController.cs`) holds the current `PlayerState`, drives `UpdateState()` every frame, and flips the player's `SpriteRenderer` to face the mouse. It also defines the abstract `PlayerState : MonoBehaviour` base class (`EnterState`/`ExitState`/`UpdateState`) in the same file.
- Concrete states live in `Assets/Assets/Scripts/Player/PlayerStates/`: `IdleState`, `WalkingState`, `CrouchState`, `CrouchIdleState`, `DeadState`. Each state is its own `MonoBehaviour` component attached to the player GameObject; `PlayerStateController` looks them up via `GetComponent<T>()` at `Start()` and caches them as public fields.
- States transition via `playerMovmentController.transitionToState(...)` (note the field/method typo `playerMovmentController` — a stable name throughout this codebase, don't "fix" it in unrelated changes).
- States read movement via `OnMove(InputValue value)` callbacks (Input System "Send Messages"/PlayerInput behavior) and read one-off keys (e.g. `LeftShift` to crouch) directly via the legacy `Input` class — the two input approaches are mixed by design here.
- States mutate shared player values on `PlayerStats` (e.g. `speed`, `concentration`) on `EnterState`/`ExitState`, and generally undo their own deltas on exit (e.g. crouch subtracts 25 concentration on enter, adds it back on exit).

### Player stats & combat

- `PlayerStats` (`Assets/Assets/Scripts/Player/PlayerStats.cs`) holds health, speed, `concentration`, and a `currentGun` reference (resolved via `transform.Find("Revolver")` — the player hierarchy is expected to have a child named `Revolver`). `TakeDamage` transitions to `DeadState` when health drops to 0.
- `RevolverScript` (`Assets/Assets/Scripts/Guns/RevolverScript.cs`) handles aiming (rotates toward the mouse), shooting, reloading, and a flashlight toggle (`T`), plus debug time-scale hotkeys (`1`/`2`/`3`). Shot accuracy is derived from `PlayerStats.concentration` and distance to the cursor via `AccuracyFromConcentration()` — lower concentration (e.g. while moving/crouching) or greater cursor distance increases bullet spread.
- `Bullet357` (`Assets/Assets/Scripts/Guns/Bullet357.cs`) is a simple projectile: travels in a straight line, destroys itself and spawns an impact prefab on trigger with anything not tagged `Player`.
- `DynamicCircleCursor` (`Assets/Assets/Scripts/Player/DynamicCursor.cs`) reads the same `AccuracyFromConcentration()` calculation to visually grow/shrink the aim cursor — accuracy math changes in `RevolverScript` should be considered alongside this script since they're expected to stay in sync.

### Sound

`ObjectSound` (`Assets/Assets/Scripts/SoundState/ObjectSound.cs`) is a base component holding a clip/position; `StepSound` (`StepsSound.cs`) extends it for footstep sounds spawned by `WalkingState`'s step coroutine (`CreateStepAtIntervals`). Note the file is `StepsSound.cs` but the class is `StepSound` (singular) — mind this mismatch when searching for it.

### Inventory

`Inventory` (`Assets/Assets/Scripts/Player/Inventory.cs`) is a `ScriptableObject` stub (`[CreateAssetMenu]`) with no fields yet — item/inventory logic is not implemented.
